# Sharely 项目复盘与面试

实现细节以 [架构](architecture.md) 为准，执行证据见 [测试](testing.md)。本文只保留项目表达、技术取舍与复盘，不重复运行手册和待办清单。

## 项目定位与个人贡献

内容社区练手项目，最初为课程小组作业；后续个人持续迭代，从 Spring Boot 单体演进为 Go + Java 双栈，并配套前端完成业务闭环。面试时区分课程阶段团队成果与后续个人改造，不将全部代码归为个人原创。

Go 承接网关、认证、互动、评论、通知与搜索；Java 保留帖子主写、关注、审核和后台。迁移依据是业务边界和可验证收益，不是替换全部 Java。

## 技术栈与选型速查

| 技术 | 项目用途 | 需要掌握的原理与取舍 |
|---|---|---|
| Go / go-zero | Gateway、RPC、依赖装配 | API/Proto 生成的是接口骨架；业务在 Logic，资源在 ServiceContext；生成代码不等于业务能力 |
| Java / Spring Boot | 保留帖子、关注与管理业务 | DI、事务代理、MVC 校验；注解隐藏了装配但没有消除事务和调用边界 |
| MySQL | 账号、认证资料 | 唯一索引、事务、隔离级别；不是所有业务数据都放 Mongo |
| MongoDB | 内容、互动、通知 | 单文档原子性不等于跨集合原子性；副本集事务保证互动明细/统计/Outbox 同提交，单节点不提供高可用 |
| Redis / go-redis | Token 状态、缓存读模型 | Set/Hash、TTL、redis.Nil、Lua、锁；同一连接池支持普通命令与 Bloom，缓存不是事实源 |
| RabbitMQ | 异步副作用分发 | 持久消息、路由、确认、重投、死信；发布确认不等于消费成功，至少一次需要消费幂等 |
| Elasticsearch | 检索与建议词 | 倒排索引、分词、近实时可见性；ES 数据可重建，不承担主写 |
| Etcd / gRPC | RPC 发现与调用 | 服务注册、租约、超时、Context 取消；本地函数返回与远程调用失败的区别 |
| Docker Compose | 开发集群与依赖编排 | 容器网络、宿主端口、健康检查、数据卷；启动顺序不等于业务就绪 |
| OTel / Prometheus / Loki | Trace、指标、日志 | Trace 看一次调用，指标看趋势，日志看细节；接入不等于覆盖所有路径 |

## 三个可以展开的工程案例

### 1. 从缓存先写到事务 Outbox

**问题：** 旧链路先改 Redis，再发布事件让 Java 落 Mongo；消息失败可能导致用户看到成功，但持久事实未写入。

**改造：** 互动服务在 Mongo 事务中写明细、统计和待发事件。提交后失效缓存；后台发布器确认 RabbitMQ 接收且未退回后删除 Outbox。MQ 故障期间主写可以提交，恢复后补发。

**边界：** 数据库提交与 MQ 确认之间仍有重复投递窗口，所以不是 exactly-once；长期失败事件可能阻塞投递，需要监控与处置。该机制仅覆盖已迁移互动事件，不覆盖所有旧事件。

### 2. 去重不只是“不插第二条”

**问题：** 同一个事件重放，即使没有新增通知，也可能把用户已读通知改回未读；不同版本乱序还可能恢复已经取消的状态。

**改造：** 收据以 eventId 去重，与通知更新放入同一事务；目标版本用于拒绝旧事件。事件唯一键解决重投，业务合并键解决同类通知归并，两者不能混为一谈。

**边界：** 收据增长和历史重放策略尚需长期规划；取消、删除及通知生命周期不能只靠 eventId 解决。

### 3. 框架统一不等于增加包装

**问题：** 同一服务维护 go-zero Redis 与 go-redis 两套池，普通缓存和 Bloom 分走不同 API，错误与 TTL 语义容易混淆。

**改造：** 业务统一原生 go-redis，保留旧配置结构以兼容 YAML；没有额外发明命令接口。补充缺失键、连接模式、TTL 和真实 RedisBloom 测试，发现并修正 RESP3 布尔回复与整数转换不兼容。

**边界：** 替换客户端也意味着原包装的熔断与 Hook 不再自动存在；真实 Cluster/TLS 部署尚未实测，不能仅凭配置单元测试宣称验证完成。

## 常见追问

- **为什么不是全 Go？** 已有 Java 业务稳定，全部重写收益有限；按职责迁移，保留清晰代理边界。
- **为什么有多个存储？** MySQL 管账号，Mongo 管内容与互动事实，Redis 和 ES 服务不同读需求；成本是运维和一致性复杂度，练手环境不意味着生产应照搬。
- **Redis 锁解决什么？** 同一个热点缓存未命中时减少并发回源，主要针对击穿；大批 Key 同时过期的雪崩还需过期分散、限流和降级。当前不能把短锁描述为完整雪崩治理。
- **预热是什么？** 提前或在首次缺失时加载数据库数据到缓存；完整集合与 TTL 原子写入，但回填和业务更新交错仍可短期陈旧。
- **ES 怎么保证一致？** 异步刷新并回查 Mongo；Sidecar 当前串行消费以减少旧事件覆盖，允许延迟且需要重建能力，不是跨库强事务。
- **MQ 挂了怎么办？** 新互动先提交 Mongo 与 Outbox，恢复后补发；其他旧发布链路不一定具备相同能力，尤其用户事件。
- **怎么证明能跑？** 说明测试分层和故障演练，并引用具体版本的结果；历史覆盖率和前一版本 Smoke 不能冒充当前验证。
- **如果重新设计？** 先收紧事实源、生命周期清理和故障恢复，必要时减少服务与中间件，而不是继续增加技术名词。

## 复习顺序

先沿“登录鉴权”和“点赞到通知/搜索”各走一遍：HTTP 契约 → Gateway → Logic → 数据写入 → 异步消费 → 失败恢复。每段回答四个问题：谁拥有数据、何时返回成功、失败后留下什么、如何重试与验证。

掌握两条链路后，再复习事务隔离、缓存竞态、消息幂等与索引原理。通用基础见 [个人复习笔记](intern.md)，不要求先背完所有中间件再读代码。
